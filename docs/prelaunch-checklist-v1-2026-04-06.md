## 6. 首批试运行策略

### 6.1 目标

- 不是大规模公测
- 小范围试运行：验证产品可用性、付费闭环、用户理解成本
- 收集真实用户反馈，发现未覆盖的边界场景

### 6.2 范围建议

| 阶段 | 人数 | 来源 | 重点 |
|------|------|------|------|
| 内测 | 5~10 人 | 团队内部 + 亲密合作伙伴 | 全链路跑通，发现明显 bug |
| 小范围 | 10~30 人 | 老板/小团队/高频办公用户 | 真实任务验证，付费闭环验证 |
| 扩大 | 30~100 人 | 有明确任务需求的真实用户 | 稳定性、并发、用户理解 |

**优先邀请**：
- 已有真实办公任务需求的人（邮件/PPT/方案）
- 小团队老板（验证 Workspace + Team 协作）
- 高频使用 AI 工具的个人用户

**避免一开始邀请**：
- 纯技术好奇型用户（不产生真实使用数据）
- 大团队（Team 按人计费未完全自动化）

### 6.3 重点观察指标

| 指标 | 目标 | 观察方式 |
|------|------|---------|
| 注册成功率 | > 95% | 查 User 表 vs VerificationCode 表 |
| 邀请接受率 | > 70% | 查 WorkspaceInvite status |
| Agent 任务成功率 | > 80% | 查 Task 表 status 分布 |
| 执行态进入率 | > 90% | SSE 连接成功率 |
| Workspace 任务闭环率 | > 60% | 查 WorkspaceTask businessStatus = completed |
| 下单成功率 | > 95% | 查 Order 表 pending → paid 转化 |
| 到账成功率 | 100% | 查 Order(paid) 对应 User 积分变化 |
| 用户理解积分体系 | 无客诉 | 收集反馈 |
| 用户理解套餐区别 | 无误购 | 收集反馈 |

### 6.4 试运行节奏

| 周次 | 内容 | 关注点 |
|------|------|--------|
| 第 1 周 | 内部测试 + 3~5 名亲密用户 | 全链路回归，修阻断 bug |
| 第 2 周 | 扩至 10~20 名真实用户 | 首次真实付费，观察到账、订阅、积分理解 |
| 第 3 周 | 扩至 30 名，观察 | 稳定性、并发、用户留存、是否继续放量 |
| 第 4 周 | 决策：继续扩大 or 回炉修 | 基于数据决定下一步 |

### 6.5 试运行退出条件

**暂停放量的信号**：
- 支付到账失败率 > 5%
- Agent 任务失败率 > 30%
- 出现数据一致性问题（积分错账）
- 出现安全问题

**可以扩大的信号**：
- 核心链路 0 阻断 bug
- 付费闭环完整可用
- 用户反馈积分体系可理解
- 无重大客诉
